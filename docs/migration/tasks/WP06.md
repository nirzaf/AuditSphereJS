# WP06 — Extend local authorization

Status: DONE for the grant/expiry/scope model (session epoch remains)
Intent: Replace the single implicit 'PREPARER' membership rule with explicit, historical, scoped capability grants, and reapply the rule inside write transactions.
Source commit and files: `nirzaf/AuditSphere@64713e808d165b4ef91ea4be4979e0f98fb2def3`; `Application/Security/RoleAssignmentService`, `RoleGrantExpiry`, `UserAccessWorkspaceQuery`; the source DbContext documents `RoleGrant` and `RoleGrantChangeEvidence`.
Destination commit and files: `packages/server/src/platform/authorization.ts`, `packages/server/src/platform/auth.ts`, `packages/server/src/modules/fieldwork/service.ts`, `packages/server/src/modules/governance/lifecycle.ts`, `prisma/migrations/202610010008_role_grants/migration.sql`, `prisma/seed.ts`.
Existing T-task links: T018 (scope model), T019 (internal identity), T021 (authorization and segregation of duties), T151 (Entra mapping).
Dependencies: WP04 scope model; the Entra adapter is preserved unchanged.
Scope: capability vocabulary; `RoleGrant` with firm/client/engagement scope, expiry and recorded revocation; check constraints that reject ambiguous scope, half revocation and inverted windows; guard requires membership plus an in-scope `ENGAGEMENT_READ` grant; each write re-checks its own capability inside the transaction.
Non-goals: A permanent development bypass; automatic Entra-role-to-local-role mapping; a grant administration UI; session/access epochs (see remaining).
Current behavior and invariants: before this work, an authenticated user with membership and `role = 'PREPARER'` could mutate the engagement. A role string now grants nothing.
Proposed contract / schema change: `capabilities` vocabulary in contracts; `RoleGrant` table; `packages/server/src/platform/authorization.ts` (`hasCapability`, `requireCapability`, `grantCoversScope`, `revokeGrant`).
Permission and transaction boundary: `InternalGuard` = identity + membership + in-scope `ENGAGEMENT_READ`. `upload`/`mapBatch` = `FIELDWORK_WRITE` checked before the external write and again inside the transaction; `finalize` = `FIELDWORK_FINALIZE`; lifecycle commands = `LIFECYCLE_COMMAND`. Grants are re-read inside the transaction, so a revocation that lands after request admission still denies the write.
Historical data / document impact: no existing membership is implicitly converted into a grant; the development seed creates explicit engagement-scoped grants.
Implementation steps: as recorded in migration 202610010008, the authorization module, the guard and the three call sites.
Relevant existing tests: `packages/server/tests/entra.test.ts`.
Minimal additional acceptance tests: no grant denies; engagement/client/firm scope coverage; sibling engagement and sibling firm deny; expired grant denies; revoked grant denies and the row is preserved; unheld capability denies; revocation between admission and write denies; ambiguous-scope, half-revocation and inverted-window inserts fail.
Commands actually executed: `pnpm exec prisma validate`; `pnpm exec prisma migrate deploy`; `pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`; `pnpm build:server`; `pnpm exec tsc -p tsconfig.tests.json --noEmit`; `pnpm test:integration`; `pnpm db:roles`; `pnpm db:seed`.
Evidence and remaining blockers: `tests/authorization.integration.ts` passed against PostgreSQL 18.6 for every denial condition above, and the database check constraints rejected ambiguous scope, partial revocation and an already-expired grant. Remaining: session/access epoch revocation, segregation-of-duties combinations (for example preparer self-review), a grant administration surface, and the wider source capability set.
Rollback / forward-recovery impact: additive; revocations are recorded rather than deleted, so history survives.
Definition of done: met for the grant/expiry/scope model used by the implemented capabilities; session epochs and SoD matrices are separate tasks.
