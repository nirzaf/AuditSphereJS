# WP04 — Define firm/client/engagement scope migration

Status: IN_REVIEW
Intent: Add canonical firm and client ownership with scoped identifiers and database constraints before any real record is migrated.
Source commit and files: `nirzaf/AuditSphere@64713e808d165b4ef91ea4be4979e0f98fb2def3`; source DbContext header documents the compound `(firm, client, engagement)` FK discipline.
Destination commit and files: `prisma/schema.prisma`, `prisma/migrations/202610010006_scope_model/migration.sql`, `packages/server/src/modules/fieldwork/service.ts`, `packages/server/scripts/provision-local-roles.ts`, `tests/database.integration.ts`.
Existing T-task links: T018 (firm/client/engagement ownership), T011 (database constraints).
Dependencies: WP02 inventory; migration 202610010005 for the same tables.
Scope: `Firm` and `Client` models; `Engagement.firmId`; `TbImport` firm/client scope; compound foreign keys so cross-firm relationships are rejected by PostgreSQL; upload derives scope from the engagement inside the transaction.
Non-goals: Giving users a broad default role; implementing role grants or the full permission model (WP06); scoping every source table in one change.
Current behavior and invariants: Before this work `Engagement.clientId` was a bare scalar with no referenced table, so any caller that knew an engagement id could attach data to it.
Proposed contract / schema change: `Client @@unique([firmId, id])`; `Engagement @@unique([firmId, clientId, id])` and FK `(firmId, clientId) → Client(firmId, id)`; `TbImport` FK `(firmId, clientId, engagementId) → Engagement(firmId, clientId, id)`.
Permission and transaction boundary: `service.upload` reads the engagement inside the same transaction that writes the document, import and audit event; the caller cannot pass scope.
Historical data / document impact: One development-only bootstrap firm/client was created for pre-scope validation rows. A production migration must use a reviewed identity map (MIG-016) and must not use this backfill.
Implementation steps: as recorded in the migration file and service change.
Relevant existing tests: `tests/database.integration.ts`, `packages/server/tests/database-roles.ts`.
Minimal additional acceptance tests: cross-firm client attached to an engagement must fail; cross-firm staged import must fail; the correctly scoped insert must succeed.
Commands actually executed: `pnpm exec prisma validate`; `pnpm exec prisma migrate deploy`; `pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`; `pnpm build:server`; `pnpm test:integration`; `pnpm db:roles`; `pnpm db:seed`; `pnpm verify:affected`; `pnpm test:unit`; `pnpm test:e2e`.
Evidence and remaining blockers: Both cross-firm assertions fail with a foreign-key violation and the scoped insert succeeds. Remaining blocker: the reviewed production identity map and the full RoleGrant model do not exist.
Rollback / forward-recovery impact: additive; dropping the scope columns would lose scope, so recovery is forward-only.
Definition of done: scope constraints enforced and tested; reviewed identity mapping for a declared cohort still outstanding.
