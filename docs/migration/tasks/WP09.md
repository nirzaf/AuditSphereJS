# WP09 — Publish accepted trial-balance versions

Status: DONE
Intent: Bridge staging finalization into authoritative, versioned engagement balances with scope, precision and lineage checks, because a FINALIZED staging import is not an accepted accounting dataset.
Source commit and files: `nirzaf/AuditSphere@64713e808d165b4ef91ea4be4979e0f98fb2def3`; `TrialBalanceImportService` sealing/acceptance, `MultiPeriodTrialBalanceService` and the sealed dataset identity in `Persistence/AuditSphereDbContext.Accounting.cs`.
Destination commit and files: `packages/server/src/modules/fieldwork/publication.ts`, `packages/server/src/modules/fieldwork/publication-controller.ts`, `prisma/migrations/202610010009_balance_publication/migration.sql`, `packages/contracts/src/index.ts`.
Existing T-task links: T050 (finalization and FSLI aggregation proof), T051 (proof gate), T081 (TB finalize).
Dependencies: WP04 scope model, WP05 precision, WP06 `TB_PUBLISH` capability.
Scope: `BalancePublication` bound to exactly one finalized import version; `PublishedBalanceRow` carrying the exact six-decimal balances and FSLI; publication command; latest/detail reads; capability, state, version, completeness and zero-sum checks.
Non-goals: Treating the existing FINALIZED staging status as published; multi-period or multi-entity datasets; mapping approval lineage (MIG-009).
Current behavior and invariants: before this work, finalization locked the staging rows but published no version, so no downstream consumer had an authoritative dataset. A publication is now the boundary and is immutable once written.
Proposed contract / schema change: `publishSchema` (importId, expectedVersion, idempotencyKey); publication and row tables; `TB_PUBLISH` added to the capability vocabulary and its database check constraint.
Permission and transaction boundary: `TB_PUBLISH` is required inside the publish transaction; the engagement row is locked; the import version must equal the caller's `expectedVersion`; the publication, its rows, the audit event and the idempotency receipt commit together.
Historical data / document impact: none; publications are appended. Republishing the same import version returns the existing publication.
Implementation steps: as recorded in migration 202610010009, the publication service and controller.
Relevant existing tests: `tests/database.integration.ts`, `tests/authorization.integration.ts`.
Minimal additional acceptance tests: staging is rejected; stale version rejected; unbalanced dataset rejected; unauthorized publisher rejected; one import publishes once; exact six-decimal values read back; publication and rows immutable; a new source version becomes the next sequence without altering the prior one.
Commands actually executed: `pnpm exec prisma validate`; `pnpm exec prisma migrate deploy`; `pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`; `pnpm build:server`; `pnpm contracts:generate`; `pnpm exec tsc -p tsconfig.tests.json --noEmit`; `pnpm test:integration`; `pnpm db:roles`; `pnpm db:seed`.
Evidence and remaining blockers: `tests/publication.integration.ts` passed against PostgreSQL 18.6 for every case above. Remaining: engine-level differential comparison against the source calculators, mapping approval lineage, multi-period/entity intake and currency-aware publication.
Rollback / forward-recovery impact: publications are immutable history; a wrong publication must be superseded by a new accepted version, never edited or deleted.
Definition of done: met for the single-dataset publication boundary; the wider MIG-008/MIG-009 intake and mapping work remains.
