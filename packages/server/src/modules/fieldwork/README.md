# Fieldwork
Purpose: own the fieldwork domain described in the architecture plan.
Owned use cases: staged CSV import, mapping against a versioned taxonomy with approved-mapping memory, immutable finalization/aggregation, deterministic sampling, and publication of accepted balance versions.
Owned tables: TbImport, TbRow, BalancePublication, PublishedBalanceRow, TaxonomyVersion, TaxonomyLine, MappingApproval, MappingMemoryEntry, AdjustmentJournal, AdjustmentJournalLine. Platform-owned ClientRepository, Document, DocumentVersion, DocumentLink, DocumentUploadSession and StoredObject records are accessed only through platform services. Taxonomy versions reference a real firm; imports, approvals, publications, documents and taxonomies expose composite keys for scope-safe module references. PostgreSQL binds every mapping approval to an import in its exact firm/client/engagement and to a taxonomy version owned by that firm; publications bind to the exact scoped import and, when present, an approval from the same engagement. Documents, immutable document versions, document links, upload sessions, trial-balance imports and tracked storage objects are linked to the same engagement in the database; each import pins the exact version that its worker parses. Document categories match the five source folders, provider references are server-side only, and version rows are append-only. Document links pin exact versions and permit only one reasoned revocation; PBC request targets are deferred until their owning PBC model is implemented. Mapping memory belongs to a real firm/client and its source approval must be for that same client.
Public services: service.ts (import/mapping/finalize/aggregate), document-uploads.ts (staff-bound short-lived upload sessions, content checks, streaming ClamAV malware screening, bounded PDF inspection, and finalize-time scope/state recheck), document-links.ts (authorized engagement/TB evidence list, link and revocation), uploads.ts (claimed unreferenced-object sweep), publication.ts, sampling.ts, taxonomy.ts (taxonomy, approval, suggestions), adjustments.ts (client audit adjustment journals). The generic upload endpoint accepts PDF and CSV only, streams multipart input through a 15 MB validating transform into a private temporary file, then streams that file to the server-side SharePoint/OneDrive Graph or S3-compatible adapter only after ClamAV reports clean. PDF bytes are additionally parsed in a worker bounded to 128 MB, five seconds, 500 pages and 10,000 annotations before any stored-object metadata or provider write; encrypted/malformed files and parser-visible active features are rejected. Tests verify compressed catalog JavaScript plus compressed indirect JavaScript actions and Link annotations, while retaining a passive compressed-text control. The lexical active-name check is defense in depth, not a complete PDF grammar or viewer-safety proof; broader compressed-object, malformed-cross-reference and viewer-specific behavior remains unverified. Scanner/inspection outages fail closed and rejected files permanently fail their upload session before storage metadata or provider writes. It retains only a five-byte signature prefix, incremental hash, and UTF-8 validator in memory. The six-state `StoredObject` protocol (UPLOADING, PENDING, REFERENCED, DUPLICATE, CLEANING, CLEANED) makes cleanup claims atomic with finalization; stale unreferenced Graph objects are verified by client folder, current version, etag, size and digest before Graph's recoverable recycle-bin delete. The compiled long-running worker and the actual `sweepUnreferencedUploads` function passed live against designated synthetic SharePoint and OneDrive folders using ephemeral PostgreSQL 18.6 and Redis; production database, backup, retention and legal-hold behavior remain outside acceptance. Malware signatures provide screening evidence, not a safety guarantee; portal/PBC upload sessions and complete hostile-PDF policy acceptance remain pending. Trial-balance CSV validation uses the shared `csv-parse` parser with explicit UTF-8/BOM, comma, quoted-field and exact-header rules. `parseTrialBalanceStream` validates one row at a time; the worker persists up to 1,000 rows per `createMany` call inside the owning PostgreSQL transaction. The current storage adapter still retrieves a bounded text payload (up to 15 MB) before parsing, and duplicate detection retains account codes for the duration of parsing; this is bounded by the existing upload and 50,000-row limits, not end-to-end streaming from object storage.
Published events: tb.import via transactional outbox. The outbox persists firm, client, engagement and import IDs as required relational columns with composite PostgreSQL ownership foreign keys; legacy import events are backfilled from their authoritative TbImport before those fields become required. Redis jobs contain only the durable outbox event UUID. The worker reloads and validates the ownership tuple from PostgreSQL before reading, claiming, completing or failing an import, so queue payloads cannot override scope.

Each new `tb.import` intent and its `BackgroundOperation` are inserted in the same transaction as the import. The operation UUID is also the outbox UUID and deterministic BullMQ job ID; event payload version 1 is intentionally empty because PostgreSQL columns carry the scope and import ID. A PostgreSQL `SKIP LOCKED` claim lease coordinates relays across worker processes, and queue insertion is recorded as published without marking the business operation complete. Trial Balance retries are safe to requeue because parsing is repeatable; row replacement, import status, operation result and outbox completion commit together. A stale non-`tb.import` operation becomes `UNKNOWN` and is listed for manual review rather than being blindly sent again. This does not claim exactly-once external effects.
Consumed events: none.
Allowed dependencies: platform services (db, authorization, storage, repository) and shared browser-safe contracts.
Forbidden dependencies: another module internals or owned-table mutations.
State transitions: lifecycle commands are owned by governance. Mapping approval, finalization and publication are guarded commands with scope, capability, expected version and idempotency. Mapping approval compares the submitted `expectedVersion` with the current `TbImport.version`; taxonomy approval compares it with the immutable taxonomy sequence and uses a `DRAFT` compare-and-set.
Critical invariants: scoped authorization re-checked inside write transactions, optimistic versions, decimal-safe six-decimal money, append-only audit and approvals, immutable finalized rows, immutable published versions, and immutable approved taxonomies. Publication requires a current mapping approval bound to an exact taxonomy version, and PostgreSQL enforces the import, firm, client and engagement lineage across those references. Documents, document versions, document links, and references from trial-balance imports and stored objects must share an engagement, and document records must reference a real engagement. Link rows pin exact provider versions and allow only one reasoned revocation; PBC targets wait for the owning request model. Mapping memory rows must reference a real client and preserve provenance to an approval for that client. Every stored object is tracked before its bytes exist; concurrent identical uploads coalesce to one authoritative import; referenced evidence is never swept. Every outbox event carries its authoritative scope in PostgreSQL and is bound to the owning engagement and, for `tb.import`, the exact import. Redis contains only the outbox UUID, which the worker resolves back to database scope before processing. Mapping suggestions are read-only and always cite the approval they came from.
